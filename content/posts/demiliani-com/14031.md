# Dynamics 365 Business Central: AL transaction isolation levels and cache usage.

> The Record.ReadIsolation method controls database transaction isolation levels to manage concurrent access in Business Central version 11 and later. Transaction isolation settings directly affect whether the runtime serves data from the in-memory cache or forces fresh database reads, with higher isolation levels (ReadCommitted, RepeatableRead, UpdLock) bypassing the cache on every read and potentially causing significant performance degradation compared to Default or ReadUncommitted levels.

[Read the post](https://demiliani.com/2026/08/05/dynamics-365-business-central-al-transaction-isolation-levels-and-cache-usage/) · Stefano Demiliani (Stefano Demiliani, MVP) · 2026-08-05 · 1031 words · tier community · **unreviewed** (machine-generated)

## Key points

- Record.ReadIsolation method allows setting isolation level for specific record instances, overriding the transaction's table-level isolation level
- Business Central cache is divided into Global (shared across users) and Private (per user/company) caches that store chunks of up to 1,024 rows per FIND call
- Only Default and ReadUncommitted isolation levels serve cached data from NST; ReadCommitted, RepeatableRead, and UpdLock force full SQL Server round-trips on every GET call
- Reading 1000 times the same record with RepeatableRead or UpdLock can be 10-100 times slower than Default isolation due to repeated database queries
- Cache synchronization between Business Central Server instances defaults to every 30 seconds and can be adjusted via CacheSynchronizationPeriod parameter

## Quotes

- "The NST record cache only serves Get() calls from cache when ReadIsolation is set to Default or ReadUncommitted." (This is the core insight explaining why higher isolation levels cause dramatic performance degradation, as they bypass caching entirely and force database round-trips.)
- "Once the isolation level goes up, it stays that way for the whole transaction." (This behavior lock-in is critical for developers to understand because it means a single elevated isolation operation affects all subsequent table reads in that transaction.)
- "This can be a measurable performance problem in production BC projects, but only under specific, fairly common conditions." (Highlights that isolation level performance impact is real and should be carefully reviewed in production code, especially for batch operations like order posting.)
