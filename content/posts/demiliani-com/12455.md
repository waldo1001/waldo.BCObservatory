# Model Context Protocol and the “too many tools” problem.

[Read the post](https://demiliani.com/2025/09/04/model-context-protocol-and-the-too-many-tools-problem/) · Stefano Demiliani (Stefano Demiliani, MVP) · 2025-09-04 · 720 words · tier community · **unreviewed** (machine-generated)

> Exposing too many tools to LLMs through MCP servers degrades performance by consuming context window capacity and causing suboptimal tool selection. The post explains the problem, shows how clients like Cursor and GitHub Copilot enforce hard limits, and recommends designing focused MCP servers scoped to specific workflows rather than monolithic servers with every available tool.

## Key points

- Too many exposed MCP tools consume context window capacity and reduce room for project context, causing slower performance and hallucinations
- Cursor enforces a 40-tool limit and GitHub Copilot a 128-tool limit to prevent context flooding
- Best practice is to build scoped MCP servers around user workflows rather than single monolithic servers with all tools
- Manually selecting needed tools per conversation is tedious but prevents overwhelming the agent

## Quotes

- "Having too many tools exposed in an MCP server can degrade the performances and the output of your LLM!" (Directly states the core problem that motivates the entire discussion about tool management)
- "if tools are crowding out the context window, there's less room for context about the current project or goal." (Explains the root cause of performance degradation and why limiting tools matters for agent effectiveness)
- "a well-designed MCP server gives agents exactly what they need to accomplish their goals without overwhelming them with choices they don't need." (Summarizes the design philosophy and best practice recommendation for building effective MCP servers)
