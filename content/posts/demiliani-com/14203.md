# Why your Business Central job queue needs idempotent external effects when integrating external systems.

[Read the post](https://demiliani.com/2026/09/01/why-your-business-central-job-queue-needs-idempotent-external-effects-when-integrating-external-systems/) · Stefano Demiliani (Stefano Demiliani, MVP) · 2026-09-01 · 1379 words · tier community · **unreviewed** (machine-generated)

> Job queue entries that call external APIs risk duplicating actions when AL transactions roll back after an external call succeeds. Use the outbox row's SystemId as a stable idempotency key that the external system enforces to prevent duplicate exports, payments, or shipments on retry.

## Key points

- AL transaction rollback does not undo external API calls, creating a gap between database state and real-world side effects.
- The anti-pattern is calling external APIs before updating local records; if the local update fails, the row retries and sends the same request again.
- External systems must deduplicate requests using a stable idempotency key (like the outbox row's SystemId) that exists before the API call.
- Delete operations require treating certain response codes (like 404) as success and deleting the local row only after the external call confirms completion.
- Idempotency must be enforced by the external API itself; a local flag set after the call rolls back with everything else on failure.
