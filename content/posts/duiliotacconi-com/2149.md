# Partial Record vs NST Caching : the strange case of Calculate Low Level Code

> Partial record optimization using SetLoadFields can unexpectedly cause performance regressions when combined with NST caching in Business Central. The post demonstrates how adding SetLoadFields to the Production BOM Version record in the Calculate Low Level Code report creates multiple SQL queries instead of leveraging the platform's caching mechanism, resulting in thousands of redundant database calls in large datasets.

[Read the post](https://duiliotacconi.com/2026/09/07/partial-record-vs-nst-caching-the-strange-case-of-calculate-low-level-code/) · Duilio Tacconi (Duilio Tacconi, MVP) · 2026-09-07 · 1413 words · tier community · **unreviewed** (machine-generated)

## Key points

- SetLoadFields prevents NST caching for partial records, unlike full records which are cached after first retrieval, causing repeated SQL queries
- The issue manifests when querying the same partial record repeatedly in loops, as each iteration triggers a separate database call instead of reusing cached results
- SetLoadFields should only be used for tables with high column counts, low retrieval ratios (under 40%), and large recordsets, not for FindFirst/FindLast/Get operations
- The performance regression exists in version 27.x and 28.x, while version 23.x cached full records and avoided the problem despite identical code
- Base Application SetLoadFields usage increased from 410 in v23.6 to 943 in v27.6, suggesting widespread potential for similar performance issues
