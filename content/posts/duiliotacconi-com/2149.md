# Partial Record vs NST Caching : the strange case of Calculate Low Level Code

[Read the post](https://duiliotacconi.com/2026/09/07/partial-record-vs-nst-caching-the-strange-case-of-calculate-low-level-code/) · Duilio Tacconi (Duilio Tacconi, MVP) · 2026-09-07 · 1413 words · tier community · reviewed (checked by Opus)

> Partial record optimization using SetLoadFields can unexpectedly cause performance regressions when combined with NST caching in Business Central. The post demonstrates how adding SetLoadFields to the Production BOM Version record in the Calculate Low Level Code report creates multiple SQL queries instead of leveraging the platform's caching mechanism, resulting in thousands of redundant database calls in large datasets.

## Key points

- Partial records loaded with SetLoadFields are not cached by the NST, while a full record read via FindLast is cached and reused.
- In Calculate Low Level Code, about 10,000 items without a Production BOM each trigger the same Production BOM Version lookup. With SetLoadFields this produced over 10,000 identical SQL statements instead of one.
- The regression appeared after an upgrade from 23.6 to 27.6 because a SetLoadFields call was added. Adding it in 23.6 shows the same lack of caching, so it is current platform design.
- Guidance cited from Microsoft's platform team: use partial records for tables with many columns, a low share of columns retrieved, and large recordsets. Single-record reads gain less.
- SetLoadFields usage in the IT Base Application grew from 410 in 23.6 to 943 in 27.6, so similar cases may exist elsewhere.

## Quotes

- "When using partial records, the caching mechanism is somewhat hardly invoked (or not working at all)." (Identifies the core issue that SetLoadFields bypasses NST caching, which is critical for understanding when partial records hurt performance)
