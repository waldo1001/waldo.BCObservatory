# API Pages vs API Queries in Business Central: When to Use Each

[Read the post](https://thinkaboutit.be/2026/03/api-pages-vs-api-queries-in-business-central-when-to-use-each/) · think about IT - Steven Renders (Steven Renders) · 2026-03-17 · 2248 words · tier community · **unreviewed** (machine-generated)

> API pages and API queries are two distinct REST API object types in Business Central with different purposes. API pages support full CRUD operations and are best for write operations, while API queries are optimized for read-only access with multi-table joins and server-side aggregation. Understanding when to use each type is critical for performance and integration design.

## Key points

- API pages support full CRUD operations (create, read, update, delete) and are designed for data exchange with single-table sources
- API queries are read-only, support multi-table server-side joins, aggregations with SIFT indexes, and automatically group results like SQL GROUP BY
- Design choices at the property level (ODataKeyFields, Enums, DelayedInsert, EntityCaption) have significant downstream consequences for consuming systems like Power Automate and Power BI
- The default choice for read-only scenarios should be API query; API pages should be used when write operations or webhook subscriptions are needed
- Separate concerns by using API pages for writes and API queries for reads, each filtered and refreshable independently

## Quotes

- "For any read-only scenario, the default choice is an API query. Not one option among two, but the default." (Establishes the primary design principle for choosing the correct integration pattern for read-only access)
- "If you design integrations with a clear separation between write and read paths, most performance and complexity problems disappear before they start." (Emphasizes that proper architectural separation is the key to avoiding performance issues in integration design)
